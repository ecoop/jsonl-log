# jsonl-log v0.2 — dual-write durability

**Status:** planning. This document is the spec of record for v0.2. The
implementation session should treat any deviation from this doc as either a
knowingly-made refinement (updated here in the same PR) or a bug.

_Last updated: 2026-08-08_

---

## Why

Rulebook is preparing for Cloud Run. Its append-only logs (`feedback`, `gold`,
`qa_log`, `source_curation`, `gold_curation`) go through `jsonl_log.append_jsonl`
and land on the container's ephemeral filesystem. Restart → data loss.

Pitchcraft (jsonl-log's other current consumer) already runs on Cloud Run with
`--max-instances=1 --min-instances=0` and has documented the same "state
doesn't survive restart" problem in its own `docs/deploy.md`. JobScout will
land in the same place.

**Goal:** feedback / gold / interaction rows survive container restart, without
paying a network round-trip on every read.

## Verified state of jsonl-log `main` @ 23ad0cc

The design brief this doc refines matches the code:

- Public surface today: `append_jsonl`, `read_all`, `read_latest`,
  `read_latest_list`, `JsonlLog`, `new_ulid`, `utc_now_iso` (see
  [src/jsonl_log/\_\_init\_\_.py](../src/jsonl_log/__init__.py)).
- `JsonlLog.append` stamps id/timestamp/schema_version and writes one line via
  the module-level `append_jsonl` under a per-instance lock
  ([src/jsonl_log/log.py:158-176](../src/jsonl_log/log.py)).
- Concurrency section of the README ([README.md:99-110](../README.md)) already
  states "A multi-worker deployment needs OS-level file locking or a dedicated
  append service — out of scope here." That's exactly the seam v0.2 slots into
  from the *other* direction: durability, not multi-writer safety.
- Tests use `tmp_path` and are fully self-contained; no existing GCS or network
  concerns to reconcile.
- `pyproject.toml` version is `0.1.1`, deps are `python-ulid` + conditional
  `typing-extensions`. No optional extras yet. Package build uses hatchling.

**Nothing in `main` conflicts with the design brief.** The brief's mention of
"single-writer, verified against pitchcraft" is accurate — confirmed via
`docs/deploy.md` (`--max-instances=1`) and `docs/v0.6-plan.md` ("Multi-instance
correctness — sidestepped via max-instances=1").

## Recommended design (summary)

- **Dual-write on append**: local disk (unchanged) + optional durable backend.
- **Reads are local-only.** Startup hydrates local from the backend.
- **Optional `durable_backend` on `JsonlLog`.** Not passing one = today's
  local-only behavior, byte-for-byte unchanged. **Free functions
  (`append_jsonl`, `read_*`) do NOT get the `durable_backend` argument** —
  callers who need durability upgrade to `JsonlLog`. (See §API surface below
  for why the surface stays narrow.)
- **Backend abstraction as `Protocol`.** No `get_backend(...)` factory in v0.2 —
  only one concrete backend (`GcsBackend`) plus "no backend"; a factory would
  buy nothing. Add one in v0.3 when Firestore / S3 / etc. arrive.
- **GCS side uses compose-API append** for true O(1) per row, with periodic
  consolidation to reset the object's `componentCount`.
- **Single-writer assumption**, matching the ecosystem's Cloud Run shape.

## API surface

### New Protocol: `DurableBackend`

```python
# src/jsonl_log/backends.py

from typing import Protocol, runtime_checkable

@runtime_checkable
class DurableBackend(Protocol):
    """Durable append-only object store for a jsonl log.

    Backends own the append semantics of their storage medium — GCS uses
    compose+consolidate to preserve per-row O(1) writes; a hypothetical S3
    backend might batch via multipart uploads. Callers see only read/append.
    """

    def read_all(self, name: str) -> str | None:
        """Full contents of `name` as text, or None if the object doesn't exist.

        Text includes the trailing newlines the backend saw on `append` — the
        return value round-trips into `path.write_text(...)` unchanged.
        """
        ...

    def append(self, name: str, line: str) -> None:
        """Append `line` (which MUST end in "\\n") to `name`.

        Must be amortized O(1) per call. Backends may batch internally, but a
        return means the row is durable at the backend's freshness guarantee.
        """
        ...
```

**Why not mirror `llm-cost-governor`'s `StateBackend` shape (`read` / `write`)?**
That contract is overwrite-only. A jsonl backend that only exposes `write` forces
the caller to do read-modify-write per append, which defeats jsonl-log's whole
O(1)-per-append point. The Protocol here is a genuine sibling, not a copy — the
Protocol+lazy-import pattern is what we borrow, not the method shape.

### Extended: `JsonlLog`

```python
class JsonlLog:
    def __init__(
        self,
        path: str | Path,
        *,
        # existing kwargs unchanged: stamp_id, stamp_time, schema_version,
        # id_field, timestamp_field, version_field, timespec, z, lock
        durable_backend: DurableBackend | None = None,   # NEW
        durable_name: str | None = None,                 # NEW — defaults to Path(path).name
        strict: bool = False,                            # NEW — hard-fail on backend errors
    ) -> None: ...

    def append(self, record: Row) -> str | None:
        """Stamp + write to local; then attempt backend.append(durable_name, line).

        Local write always happens first. Backend failure with strict=False logs
        a warning and returns normally; with strict=True the exception propagates
        after the local write has already committed (see §Failure semantics).
        """
        ...

    def hydrate(self) -> None:
        """Populate local from backend at startup.

        Contract:
          * No backend → no-op.
          * Backend has content → atomically overwrite local (temp-file + rename).
            GCS is authoritative. Any local content is discarded.
          * Backend is empty → local is left untouched. (See `bootstrap()` for
            the one-time push-local-up case.)

        MUST be called before any `.append()` calls when durability matters.
        Not thread-safe against concurrent readers/writers on the log; call
        during startup, single-threaded.
        """
        ...

    def bootstrap(self) -> None:
        """One-time: push local content up to backend when backend is empty.

        For consumers adopting durability on an existing local log file. Idempotent
        when the backend already has content (no-op). Not safe under concurrent
        writers. `hydrate()` after `bootstrap()` should be a no-op.

        Consumers with no historical log (rulebook today) never need this.
        """
        ...
```

### Concrete: `GcsBackend`

```python
# src/jsonl_log/backends.py (same file — see §Module layout)

class GcsBackend:
    """Store a jsonl log as one GCS object per name, appended via GCS compose.

    Each `.append(name, line)`:
      1. Uploads `line` to a per-append temp object.
      2. Composes [target, temp] → target (server-side, no download).
      3. Deletes the temp object.

    Every `consolidate_every` appends, rewrites the target as a single flat
    object to reset its `componentCount` (GCS caps components per object). The
    rewrite is O(N) in the log's size — a periodic latency spike, not a per-row
    cost. Chosen default keeps this rare enough not to matter on the write path.

    google-cloud-storage is imported lazily on first use; importing this
    module never triggers the import (mirroring llm-cost-governor.state).
    """

    def __init__(
        self,
        bucket: str,
        *,
        prefix: str = "",
        consolidate_every: int = 1000,
    ) -> None: ...

    def read_all(self, name: str) -> str | None: ...
    def append(self, name: str, line: str) -> None: ...
```

Object names in the bucket: `{prefix}{name}` for the target;
`{prefix}{name}.tmp.{ulid}` for per-append temp objects (deleted after compose).
Content-Type: `application/x-ndjson`.

## Failure semantics — the strict/non-strict split

Local write is the fast, always-first step. Backend write is best-effort under
default settings; opt-in strict for audit-critical logs.

| `strict` | Local write | Backend write | Result |
|---|---|---|---|
| False (default) | Succeeds | Succeeds | Returns normally. |
| False (default) | Succeeds | Raises | Warning logged; returns normally. Row is on local disk only; on next successful append the row *before* it stays lost from GCS (see below). |
| True | Succeeds | Succeeds | Returns normally. |
| True | Succeeds | Raises | Exception propagates. **Local file already has the row.** No rollback. |
| any | Raises | (not attempted) | Local write is done under a lock before the backend call; a local write failure means the row is nowhere. Exception propagates. |

**Why local-first?** A container that can't write to its own filesystem is
already in an unrecoverable state; ordering the local write first keeps the
in-container view of "what's in the log" consistent with what future reads
see, whether or not GCS is up.

**The "silent GCS gap" caveat.** In non-strict mode, if a backend append fails,
the row is on local disk but not in GCS. The *next* successful backend append
composes only the newer row onto GCS — the missed row is not retroactively
pushed. On container restart, `hydrate()` pulls GCS-authoritative state, and
that missed row disappears from the container's view. **This is intentional:**
non-strict logs are HITL signal (thumbs, curation clicks), not compliance
records; losing one on a GCS outage is preferable to failing the user's
request. Consumers with different tolerance opt into `strict=True` and handle
retry themselves. This trade must be called out in the README section and the
consumer-adoption checklist.

## Test plan — named cases

Every unit test uses `tmp_path` for local storage and a `FakeDurableBackend`
for the durable side. No test in the default suite requires
`google-cloud-storage` as an import. The integration test is skipped unless
`GCS_TEST_BUCKET` is set.

### `test_backends_protocol.py`

Covers the Protocol seam.

- `test_fake_backend_satisfies_protocol` — an in-test class with the two
  methods is accepted by `isinstance(..., DurableBackend)` (runtime_checkable).
- `test_gcs_backend_satisfies_protocol` — same, for the real class, without
  triggering the lazy `google.cloud.storage` import.
- `test_arbitrary_class_satisfies_protocol` — proves a Firestore-shaped
  future backend drops in with no inheritance.

### `test_dual_write.py`

Covers `JsonlLog` with `durable_backend=` set. All use `FakeDurableBackend`.

- `test_no_backend_is_unchanged` — existing tests still pass without regression
  (essentially a smoke re-run of `test_jsonllog.py`'s round-trip with
  `durable_backend=None`, expressed here for clarity).
- `test_append_writes_local_and_backend` — one append produces one local line
  AND one `backend.append(name, line)` call with matching content.
- `test_default_durable_name_is_path_basename` — `JsonlLog("data/feedback.jsonl", ...)`
  calls `backend.append("feedback.jsonl", ...)`.
- `test_explicit_durable_name_overrides_default`.
- `test_backend_failure_soft_by_default` — with `FakeDurableBackend.fail_next=True`,
  the append returns normally, the row is on local disk, and a warning is
  emitted (capsys / caplog).
- `test_backend_failure_strict_raises` — with `strict=True`, the exception
  propagates; the row IS still on local disk (documented behavior).
- `test_read_helpers_are_local_only` — `read_all` / `read_latest` /
  `read_latest_list` never call the backend.

### `test_hydrate.py`

Covers `hydrate()` and `bootstrap()`.

- `test_hydrate_no_backend_is_noop`.
- `test_hydrate_populates_empty_local_from_backend` — backend has content,
  local file doesn't exist → after hydrate, local matches backend byte-for-byte.
- `test_hydrate_overwrites_diverged_local` — both sides have different content;

- `test_hydrate_empty_backend_leaves_local_alone` — backend has no object,

- `test_hydrate_is_atomic_on_local_side` — simulated mid-hydrate failure never

- `test_bootstrap_pushes_local_when_backend_empty`.
- `test_bootstrap_noop_when_backend_has_content`.
- `test_bootstrap_no_backend_is_noop`.

Covers `GcsBackend` against a fake `google.cloud.storage` client (same

- `test_gcs_append_subsequent_composes` — target exists; append does

- `test_real_gcs_hydrate_after_restart` — write via one `JsonlLog`, discard the

- `test_real_gcs_consolidation_end_to_end` — enough appends to trigger one

CI never runs this suite by default. Local dev sets `GCS_TEST_BUCKET=...`
against a personal project bucket.

## Open questions — for the implementation session

These are things the plan cannot fairly resolve without touching real GCS or
looking up current docs.

1. **`consolidate_every` default.** GCS's per-object `componentCount` limit is
   real but I did not want to guess its current value from memory. Check
   Google's storage docs; pick a default that gives ~10× headroom before the
   cap. `1000` is a plausible default if the cap is `5000+`; drop to `100` if
   the cap is `~1000`. Document the choice with the source link.

2. **Content-Type.** `application/x-ndjson` is the semi-standard MIME for
   NDJSON but not universally accepted. `application/jsonl+json` and
   `application/json-lines` also appear in the wild. Pick and stick.

3. **Consolidation strategy — inline or deferred.** Plan-of-record is inline
   ("append number N triggers rewrite"). Alternative: emit a
   `NeedsConsolidation` signal and let the caller schedule it off the write
   path. Inline is simpler; if the O(N) spike bites rulebook in practice, add
   deferred in v0.3. Confirm inline is acceptable before implementing.

4. **`bootstrap()` in v0.2 vs later.** The design brief doesn't call for it;
   this plan added it. Rulebook doesn't need it (fresh logs on Cloud Run).
   Pitchcraft *would* need it (existing per-user ledgers to preserve). If
   pitchcraft's durability rollout isn't near-term, `bootstrap()` can slip to
   v0.3 to keep v0.2's surface tighter.

5. **`hydrate()` idempotency guard.** Plan says "call once at startup".
   Should `hydrate()` refuse to run if local has more rows than the backend
   (i.e., appends happened after startup but before hydrate)? An assertion
   here would catch consumer bugs; an unconditional overwrite silently loses
   data. Recommend a `warn-and-refuse` mode with a `force=True` escape.

6. **Backend error type.** Do we wrap `google.cloud.exceptions.GoogleAPIError`
   in our own `DurableBackendError`, or let it bubble raw? Wrapping keeps
   consumer `except` clauses backend-agnostic; not wrapping preserves the
   original traceback. Recommend a thin `DurableBackendError` wrapper that
   `raise ... from original` for provenance.

7. **`logging` namespace.** Warnings go to `logging.getLogger("jsonl_log")` or
   `logging.getLogger("jsonl_log.durable")`? Pick and document so consumers
   can silence/route it.

8. **Where does the append-counter for consolidation live?** In-memory on the
   `GcsBackend` instance (resets on restart, fine). Not persisted to GCS.
   Consequence: consolidation cadence is per-process-uptime, not per-log-total.
   Acceptable — the cap is a safety net, not a timing guarantee.

9. **Should `JsonlLog` accept a shared backend across multiple logs?** Currently
   yes, by construction — one `GcsBackend(bucket=...)` instance can be handed
   to N `JsonlLog` instances with distinct `durable_name`s. Confirm this is
   the intended pattern (it fits Cloud Run consumer shape) and document it.

10. **`google-cloud-storage` version floor.** Per the design brief: floor-only,
    recent enough for stable compose-API. Check the package's changelog for
    the earliest version where the compose semantics used here are stable;
    pick that floor and document it. Don't upper-cap.

## Non-goals for v0.2 (concur with design brief)

- Firestore, S3, Azure Blob backends. Protocol admits them; do not build.
- Log rotation / archival.
- Encryption beyond GCS defaults.
- Compaction / tombstones — jsonl-log has no update semantics; don't grow that
  surface.
- Multi-writer correctness — v0.3 candidates in design brief still hold.

## Explicit non-features this plan adds beyond the brief

- **No `get_backend(...)` factory** — only one real backend + `None`, no
  selection to make. Adding a factory now is speculative surface. Reconsider
  in v0.3.
- **Free functions (`append_jsonl`, `read_*`) stay untouched.** The design brief
  said "on `JsonlLog` / `append_jsonl`"; this plan narrows to `JsonlLog` only.
  Reason: hydration has no natural home at the free-function layer (they're
  stateless), and splitting the surface makes the strict/non-strict/hydrate
  contract harder to reason about. Free-function consumers who need durability
  are one `JsonlLog(...)` call away.
- **`bootstrap()` added.** Needed for pitchcraft's historical ledgers if that
  adoption is near-term; can slip to v0.3 otherwise (see open question #4).
- **No `LocalFileBackend`.** In llm-cost-governor there's one because both
  local and GCS satisfy the same *overwrite* contract. In jsonl-log the local
  file IS the "no backend" path — a `LocalFileBackend` that also writes to a
  local file would just double-write to disk for no benefit.
